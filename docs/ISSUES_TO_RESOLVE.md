## ISSUE-001：管理控制台左下角显示“服务未知 / 版本未知”

- **提出时间**：2026-10-28
- **现象**：管理控制台左下角显示绿色圆点，以及“服务未知”“版本未知”。用户提供的截图对应此现象。
- **显示位置**：`frontend/src/admin/components/AdminConsoleShell.vue` 的 `sidebar-foot`。
- **实际数据路径**：
  1. `AdminConsoleShell` 使用 `AdminNext.vue` 传入的 `workerStatusLabel` 和 `dbVersionLabel`。
  2. `workerStatusLabel` 读取 `live.workerConfig.DIAGNOSTICS.database`：没有 `workerConfig` 时，在已完成一次管理数据加载后返回 `unknown`。
  3. `dbVersionLabel` 读取 `live.dbVersion.code_db_version`，再回退到 `workerConfig.DIAGNOSTICS.database.code_version`；两者都没有时返回 `unknown`。
  4. 这两项数据分别来自 `/api/admin/worker/configs` 和 `/api/admin/db_version`，由 `loadAdminViewSnapshot` 按当前管理视图选择性读取。
- **已确认的代码原因**：
  - 左下角的绿色圆点是 CSS 固定绘制的 `var(--success)` 颜色（`admin-next.css`），没有绑定真实健康检查结果。因此“绿色”不能证明服务健康。
  - `unknown` 是前端兜底文本，表示用于显示的配置或版本数据为空；它不是 Worker `/health_check` 返回的服务状态。
  - 管理数据读取使用 `safeRead`，请求失败会被捕获并转换为 `null`，但侧栏仍把它显示成“未知”，没有把“请求失败”单独显示出来。
  - 当前视图按功能边界读取数据。只有 `overview` 和 `ops` 视图请求 `workerConfig`、`dbVersion`；如果从其他视图直接进入，`live.fetchedAdmin` 可能已经为真，但这两项数据尚未请求，侧栏也会显示“未知”。
- **最可能的触发条件**：
  1. 从非 `overview` / `ops` 视图直接打开或恢复管理控制台，当前视图没有加载服务配置和数据库版本；或
  2. `/api/admin/worker/configs`、`/api/admin/db_version` 其中一个或两个请求失败，错误被记录到 `live.errors`，侧栏仍只显示“未知”。
- **不能仅凭截图确认的内容**：截图不能区分“当前视图未请求数据”和“接口请求失败”，也不能证明 Worker、D1 或 Pages 实际不可用。需要结合浏览器 Network、`live.errors` 和两个接口响应现场确认。
- **影响**：用户会把数据尚未加载、接口失败和真实服务异常混为一谈；绿色圆点还会造成与文字相反的健康暗示。
- **最小处理方向**：让侧栏状态使用一个与当前视图无关的服务/版本读取结果，并分别表达“加载中”“读取失败”“服务可用/需要检查”；绿色圆点必须跟随实际状态，不能固定为成功色。保留现有按功能视图加载业务数据的边界。
- **验证状态**：代码已修复并随本轮版本发布，待管理员浏览器现场确认具体页面状态。

## ISSUE-002：验证器和地址使用两套分发方式

- **提出时间**：2026-10-28
- **现象**：验证器列表中使用下拉框选择用户，再点击“分发”；地址的用户绑定则放在用户管理弹窗中，地址本身还另外提供凭证和分享包入口。用户认为这种下拉分发方式割裂且不自然，希望验证器和地址统一为一种分发方案。
- **验证器当前路径**：
  1. `AdminAuthenticators.vue` 为每个验证器渲染用户下拉框和“分发”按钮。
  2. 选择用户后调用 `POST /api/admin/authenticators/:id/assignments`。
  3. Worker 将 `user_authenticator_access.direct_assigned` 设为 `1`，用户随后通过 `/user_api/authenticators` 直接看到验证码。
  4. 同一行还提供“分享”按钮，调用 `/api/admin/authenticators/:id/shares` 创建另一种可过期的链接；用户通过 `/open_api/authenticator_share` 打开，再调用 `save-share` 保存访问关系。
- **地址当前路径**：
  1. 地址表格的“更多”菜单没有地址行内的用户下拉分发；管理员先进入用户管理，再通过 `POST /api/admin/users/bind_address` 绑定地址。
  2. 这种绑定写入 `users_address`，地址用户侧再通过已有地址管理逻辑使用。
  3. 地址自身还可以通过“凭证”显示/轮换地址 JWT，或者通过 `/api/admin/address/:id/share_tokens` 创建地址分享包。
- **已确认的结构差异**：
  - 验证器的直接分配是 `user_authenticator_access.direct_assigned`，验证器分享是 `authenticator_share_tokens`；地址的直接绑定是 `users_address`，地址分享是 `address_share_tokens`。
  - 两类分享链接的路径、表、ID 类型、权限字段和用户接入接口都不同：验证器使用 `/a/:token`，地址使用 `/i/:token`。
  - 因此这不是单纯的按钮样式不一致，而是资源授权模型和管理入口都不一致。
- **结论**：用户看到的“下拉分发”确实是验证器独有的直接授权入口；地址采用“从用户侧绑定地址”的另一套入口。两者都能表达“把一个受保护资源授予某个用户”，却没有共享一个分发对象或统一的操作流程。
- **最小统一规划**：把“分发”定义成统一的持久凭证流程，验证器和地址都从资源行进入同一个分发界面；凭证默认永不过期，只在管理员主动刷新或撤销时变化，底层再分别适配现有关系表。先统一用户可见的入口和状态，再决定是否合并底层表，避免为了界面统一直接破坏现有登录接口。
- **待定决策**：需要明确统一方案是“指定用户的访问授予”还是“可转发的分享链接”；如果两者都保留，应在同一个分发流程中明确区分目标和生命周期，而不是继续用两个互不相干的入口。
- **验证状态**：代码已按统一分享链接方向发布；旧授权接口保留兼容，待管理员浏览器现场确认。

## ISSUE-003：地址同时暴露凭证和分享连接，分发方案重复

- **提出时间**：2026-10-28
- **现象**：地址列表和地址详情同时出现“凭证/轮换”和“分享/分享包”相关入口；访问包页面还可以存在多个分享方案。用户希望凭证和分享连接二选一，只保留一个方案，并与验证器使用同一种分发逻辑。
- **实际代码路径**：
  - 地址行展示 `credentialVersion`、`packages` 两个独立字段；详情操作同时提供“显示凭证”“轮换凭证”“创建分享包”“撤销分享包”。
  - 地址凭证由 `/api/admin/address/:id/credential` 或 `/rotate_credential` 生成，格式化为地址登录 JWT/登录信息。
  - 地址分享包由 `/api/admin/address/:id/share_tokens` 创建，写入 `address_share_tokens`，可以有多个、带标签、权限范围、过期时间和撤销状态。
  - 验证器也同时拥有直接分配和分享链接两条路径，但其分享链接仅在 `authenticator_share_tokens` 中管理。
- **已确认的语义差异**：
  - 地址凭证是地址本身的长期访问凭据，轮换凭证通过 `credential_version` 使旧凭证失效。
  - 地址分享连接是可撤销、可过期、可带范围的临时访问授权，天然支持多个并存的外部接收者。
  - 所以当前两个入口在后端并非同一对象的两个名字，而是两种不同的安全生命周期；界面把它们并列展示，才造成“多个分享方案没有意义”的感受。
- **结论**：问题的根因是产品层没有选定唯一的“资源分发对象”。目前地址同时暴露长期凭证、单用户绑定和多条分享连接，验证器又有直接分配和分享连接，用户必须理解多个授权模型才能完成一件“给别人访问”的事情。
- **建议的统一方向**：以“持久、可主动撤销或刷新”的访问凭证作为唯一的用户可见分发方式，验证器和地址都从同一分发流程创建、查看、复制、刷新和撤销；不设置自动过期，也不做只显示一次处理。
- **必须保留的兼容边界**：地址 JWT 和现有登录接口继续作为持久凭证使用；刷新由管理员主动触发，不能由界面或后台定时自动失效。
- **验证状态**：管理员界面已按持久凭证方向发布，Pages 和 Worker 健康检查通过；待管理员浏览器现场确认。

## ISSUE-004：地址复制按钮位置造成复制对象误解

- **提出时间**：2026-10-28
- **现象**：图二地址列表的“复制”按钮位于每行最右侧操作区，和“查看邮件”“更多”并列；用户容易误以为它复制凭证、访问包或其他敏感信息。用户希望像图三邮件发件人地址那样，在左侧地址文本旁放置复制图标。
- **实际代码路径**：
  - `AdminResourceWorkspace.vue` 的 `addressActions` 分支在最右侧渲染复制按钮。
  - 当前按钮实际执行 `actions.copyText(row.address)`，复制内容只有地址字符串，不会复制凭证或分享连接。
  - 地址主单元格使用通用 `entity` 渲染，只显示地址、备注和标签，没有地址旁的复制 affordance。
- **结论**：这是信息架构和视觉归属问题，不是复制内容错误。功能本身复制的是地址，但按钮远离地址字段，且与其他操作共用文字按钮样式，导致用户无法快速判断复制对象。
- **最小处理方向**：把复制动作从地址行尾部操作列移入地址主单元格，紧跟地址文本显示复制图标；按钮的 `aria-label` 和 `title` 明确为“复制地址”。地址行尾部保留查看邮件和更多操作，凭证、分享连接等敏感动作继续留在明确命名的菜单或分发面板中。
- **联动要求**：如果 ISSUE-002、ISSUE-003 采用统一分发面板，分发链接或凭证的复制动作必须在分发结果旁单独命名，不能复用“复制地址”的按钮。
- **验证状态**：代码已发布并补充地址复制按钮回归断言，待管理员浏览器现场确认。

## ISSUE-005：用户中心仍保留地址凭证入口（本轮暂不改）

- **发现时间**：2026-10-29
- **发现位置**：`frontend/src/views/index/AccountSettings.vue`、`AddressManagement.vue` 和对应用户端 API。
- **问题**：管理员界面已经统一使用分享链接，但用户中心仍允许查看地址凭证、使用地址 JWT 切换邮箱，并保留凭证绑定/解绑路径。这是另一条真实的访问路径，和本轮管理员分发方案并存。
- **为什么本轮不改**：这些入口涉及当前登录态、密码修改、用户绑定地址和历史会话；直接删除会造成已有用户失去访问能力，需要单独设计迁移、提示和失效策略。
- **状态**：已确认这是统一凭证链路的一部分，用户中心凭证入口保留，不再作为待移除问题。

- **发现时间**：2026-10-29

- **为什么本轮不改**：需要先盘点调用方和已有数据，再决定是迁移到分享链接、保留内部兼容，还是增加一次性转换；本轮直接删除接口会破坏现有用户授权。
- **状态**：管理员界面的直接分发入口已移除；旧接口和已有关系保留兼容，后续只在完成数据迁移方案后再收紧。

## ISSUE-007：访问包列表仍会展示历史撤销/过期记录（本轮暂不改）

- **发现时间**：2026-10-29
- **发现位置**：`/api/admin/access_packages` 和管理员访问包列表。
- **问题**：本轮已让每个地址和验证器最多保留一个有效分享链接，但历史链接仍会保存在数据库中。访问包列表按历史记录查询时，用户仍可能看到多个已撤销或已过期的方案，从视觉上继续产生“很多分享方案”的感觉。
- **为什么本轮不改**：历史记录对审计和追责有价值，需要先决定列表默认是否只显示当前有效链接，以及历史记录是否移入单独筛选或审计视图；不能直接删除历史行。
- **状态**：访问包视图默认改为只看当前有效凭证，历史撤销/过期记录仍可通过“全部”筛选查看。

## ISSUE-008：资源表在详情关闭后仍保留上次点击行的高亮

- **提出时间**：2026-10-29
- **现象**：用户鼠标已经移动到其他位置，但地址页仍高亮上一次点击的地址行。截图中第一行 `newcodex3@colin.fnrry.com` 保持蓝色背景，鼠标位于下方其他行附近，页面没有显示对应的详情抽屉。
- **实际代码路径**：
  1. `AdminNext.vue` 的 `selectRow(kind, id)` 将资源 ID 写入 `ui.selected[kind]`，并把地址、用户、域名、通知、运行维护等资源的 `detailOpen` 设为 `true`。
  2. `AdminResourceWorkspace.vue` 的所有资源表行都使用 `actions.isSelected(panel.kind, row)` 添加 `is-selected` 类。
  3. `isSelected` 只比较 `ui.selected[kind] === row.id`，没有同时判断详情抽屉是否仍然打开。
  4. `closeDetail()` 目前只执行 `detailOpen.value = false`，不会清除对应的 `ui.selected` 值。
  5. CSS 的 `tr.is-selected` 使用蓝色背景，因此上次点击的行在详情关闭后仍然保持视觉选中状态。
- **排查到的相似页面**：
  - 地址（`identity`）、用户（`users`）、域名/路由（`routing`）、通知/投递（`delivery`）和运行维护（`ops`）共用这套资源表和详情抽屉逻辑，存在相同的残留高亮条件。
  - 收件箱（`flow`）的高亮有不同语义：分栏阅读器打开时必须保留当前邮件高亮，用于说明右侧正在查看哪一封；返回列表时现有逻辑会清除邮件选中状态，这类高亮属于合理的上下文状态。
  - 域名筛选下拉框中的选项高亮、侧边栏当前页面高亮、批量勾选状态也属于明确的当前状态，不应按本问题一并清除。
- **结论**：问题不是所有高亮都错误，而是资源详情关闭后，列表仍把“上次点击过”当成“当前上下文选中”。截图对应地址资源表的残留选中状态；同一共享实现可能影响其他带详情抽屉的资源页。
- **最小处理方向**：让资源表行的高亮同时受详情上下文控制，或在关闭详情时只清除对应资源的选中 ID；保留收件箱打开详情时的邮件高亮、批量勾选、筛选选中和导航当前态。
- **验证状态**：已记录，尚未修改代码；需要在地址、用户、域名、投递、运行维护和收件箱打开/关闭详情两种状态下分别确认。

## ISSUE-009：访问包页面的产品价值和凭证职责不清

- **提出时间**：2026-10-29
- **现象**：用户询问访问包页面的实际意义。当前页面看起来像一个独立的资源管理页面，但地址和验证器页面已经分别提供凭证生成、刷新、查看和撤销入口，访问包页面与这些入口存在重复。
- **实际代码路径**：
  1. 管理控制台的 `access` 视图调用 `/api/admin/access_packages`，读取 `address_share_tokens` 的地址分享记录，同时读取管理员验证器列表。
  2. 页面表格显示地址或验证器、凭证类型、权限范围、状态、是否过期、最后使用时间，并与审计/访问记录并列展示。
  3. 原先 `buildAdminShareRows` 为每条地址记录生成固定的 `path: '/i/:token'`，复制按钮复制的是路径模板而不是实际 token；本地改造已移除该操作列。
  4. 验证器分享记录使用另一套 `authenticator_share_tokens`，现在由总览读取其当前凭证状态。
- **当前实际价值**：页面现在作为地址和验证器的持久凭证总览，提供跨资源查看当前凭证状态、类型、使用时间和审计记录的入口；实际刷新、撤销和凭证查看仍回到对应资源页执行。
- **已确认的问题**：
  - 地址页和验证器页仍分别承担凭证操作，访问包总览不应重复生成或复制凭证；
  - 历史撤销/过期记录可能继续存在，但不应和当前有效凭证混淆；
  - 总览必须覆盖地址和验证器，不能只列地址分享记录。
- **与当前持久凭证规则的关系**：总览只呈现凭证状态和审计信息，不引入一次性显示、自动过期或自动失效；管理员仍通过资源页主动刷新或撤销。
- **验证状态**：已按“凭证总览”方向完成本地实现：地址和验证器记录统一展示，移除了无效的模板复制动作；待生产发布和管理员浏览器现场确认。
